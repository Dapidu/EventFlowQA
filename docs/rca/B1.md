# RCA B1 : des places VIP sont vendues alors que le carré est plein

## Symptôme observé

Un client commande plus de billets VIP qu'il n'en reste (4 alors qu'il en reste 3). L'API accepte la commande (`201 Created`) au lieu de la refuser (`409 Conflict`). Ensuite, l'API et le site affichent « 0 place restante » : rien ne montre que le quota est dépassé.

Le test `test_rm1_cannot_order_more_than_available_stock` échoue (`assert 201 == 409`).

Contexte : branche `mission-lundi`, mode bug activé (`SEED_BUGS=true`), 23/11/2026. Signalé par le support : « des places VIP vendues alors que le carré est plein ».

## Impact (pour l'utilisateur, pour l'entreprise)

**Pour l'utilisateur**

- Un client paie une place VIP qui n'existe pas physiquement : refoulé à l'entrée ou déclassé le jour du festival, après avoir payé.
- Annulation et remboursement après coup, souvent tardifs : frustration, perte de confiance dans la billetterie.

**Pour l'entreprise**

- Coûts directs : remboursements, compensations, gestion des réclamations par le support.
- Risque sécurité et légal : la capacité d'un espace (le carré VIP) est souvent liée à des règles de sécurité. Dépasser la jauge peut être interdit.
- Risque amplifié par la vente flash de mercredi : de nombreuses commandes simultanées sur une catégorie à petit quota (3 places).
- Défaut masqué : l'API affiche 0 place restante, jamais un nombre négatif. Personne ne voit le problème avant le jour de l'événement, sauf en interrogeant la base.

## Cause racine

**Produit :** le contrôle de stock RM1 (`orders.py:99`) dépend d'un indicateur de configuration global (`settings.seed_bugs`). Quand il est actif, la règle métier est désactivée. Le quota n'est protégé que par ce `if` dans le code, sans aucune garantie côté base de données.

**Processus :** les filets de sécurité ne couvrent pas ce cas. Le test de cohérence de la base vérifie une règle différente de celle du code (`paid` seulement, au lieu de `paid` + `pending`), le `max(0, …)` masque le dépassement dans l'API, et la CI ne teste jamais la configuration où le défaut se produit.

## Actions correctives

- **Produit :**
  - Retirer `and not settings.seed_bugs` de `orders.py:99` : le stock est toujours contrôlé.
  - Protéger le quota au niveau de la base, en plus du code : verrouiller la catégorie pendant la création de la commande (`SELECT … FOR UPDATE` / `with_for_update()` en SQLAlchemy). Sans verrou, deux commandes simultanées pendant la vente flash peuvent lire « 3 places » en même temps et les prendre toutes les deux.
  - Journaliser une alerte si `quota - vendus` devient négatif, au lieu de le ramener silencieusement à 0.
- **Processus de test :**
  - Corriger `test_no_category_is_oversold` : compter `paid` et `pending` non expirées, comme `category_sold`.
  - Ajouter un test de concurrence : N commandes simultanées sur une catégorie de quota 3 → exactement 3 billets réservés.
  - Faire tourner la CI aussi avec `SEED_BUGS=true` (matrice), et rendre le statut CI obligatoire pour fusionner.
  - Règle de revue de code : refuser toute condition qui désactive une règle métier (RM1 à RM7) selon un réglage.

**Action concrète immédiate :** pull request qui supprime `and not settings.seed_bugs` à la ligne 99 de `backend/app/routers/orders.py` et remplace `o.status = 'paid'` par `o.status IN ('paid', 'pending')` à la ligne 54 de `qa/tests/api/test_db_consistency.py`.

## Comment vérifier que c'est corrigé

1. Démarrer l'application dans la configuration où le défaut apparaissait :

   ```powershell
   $env:SEED_BUGS="true"; docker compose up -d backend
   ```

2. Le test RM1 doit passer :

   ```powershell
   pytest tests/api/test_booking_rules.py::test_rm1_cannot_order_more_than_available_stock
   ```

   Attendu : `1 passed` (statut `409`, `{"detail": "Not enough stock for VIP"}`).

3. La base ne doit contenir aucune catégorie en dépassement, commandes `pending` comprises :

   ```powershell
   docker compose exec db psql -U eventflow -d eventflow -c "SELECT c.id, c.name, c.quota, SUM(oi.quantity) AS reserves FROM ticket_categories c JOIN order_items oi ON oi.category_id = c.id JOIN orders o ON o.id = oi.order_id WHERE o.status IN ('pending', 'paid') GROUP BY c.id, c.name, c.quota HAVING SUM(oi.quantity) > c.quota;"
   ```

   Attendu : `(0 rows)`.

4. Le test de cohérence corrigé échoue si on réintroduit le bug (preuve qu'il détecte désormais les `pending`), puis passe une fois le bug corrigé.

5. Non-régression : `pytest tests/api -n auto` → `59 passed` ; en CI, le job est vert dans les deux configurations `SEED_BUGS`.
